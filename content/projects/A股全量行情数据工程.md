## 为什么做这件事

量化的本质是用数据流驱动资金流，万丈高楼不能凭空而起，而数据就是建造这座高楼所需要的地基，我在进行多因子量化模型研究时就时常受到数据集不够的问题干扰，而自己通过数据服务商的api拉取耗时耗力，且费用过高，api接口限流严重，于是干脆心一横，购买了服务商的源头数据包，并将其规范整理封存，故而这个项目提供了详尽的A股量价数据，主要用于本地建模研究，出于复杂度和性能考虑，本项目中的数据构建完后就已经冻结，后续不再更新，因为只是本地研究、复现量价因子，这份数据已经足够充实了。

源数据是买的，但分区方案、三个构建/校验脚本和 README 是我写的。这份报告主要讲这部分。

## 数据最后是什么样

| 项目        |                                   结果 |
| ----------- | -------------------------------------: |
| 时间范围    |                2009-01-05 ~ 2026-10-23 |
| 分钟 K 线   | 3,647,449,745 行，214 个文件，37.1 GiB |
| 日线        |     14,790,365 行，18 个文件，0.98 GiB |
| 证券主表    |             5,928 只 × 17 列，191 KiB |
| 总大小      |                               38.1 GiB |
| 股票-日样本 |                          15,110,765 个 |

目录按年月切开：

```text
A股行情数据/
├── minute/1min/year=2009/month=01.parquet
├── ...
├── minute/1min/year=2026/month=10.parquet
├── daily/year=2009.parquet
├── ...
├── daily/year=2026.parquet
├── basic/dim_instrument.parquet
├── _manifest.json
└── _build/
    ├── 01_partition.py
    ├── 02_verify.py
    ├── 04_audit.py
    └── _audit.json
```

分钟表 10 列：日期、代码、K 线结束时间、OHLC、成交量、成交额、复权因子。日线 33 列，多了昨收、涨跌停价、停牌、ST、上市天数、估值、股本和市值。证券主表 17 列，实际常用的是 `industry` 和 `list_date`。

分钟表的主键是 `(trade_date, ts_code, trade_time)`，日线是 `(trade_date, ts_code)`。三张表之间只靠 `ts_code` 关联，没有外键，也没有全局索引。

## 为什么按月分区

源包是“每股一个文件”，按股票查很舒服，但查“某一天全市场”要打开几千个文件。按天切又反过来：横截面快，单股票历史要扫几千个文件。

三种切法我比较过：

| 切法         |    文件数 | 某一天全市场         | 某只股票全历史         |
| ------------ | --------: | -------------------- | ---------------------- |
| 每股一个文件 | 约 6.6 万 | 要开几千个文件       | 1 个文件               |
| 每天一个文件 |  约 4,300 | 1 个文件             | 要开几千个文件         |
| 每月一个文件 |       214 | 1 个文件内按行组剪枝 | 214 个文件，可按年并行 |

最后选了按月。214 个文件的元数据开销可以忽略，横截面查询只读一个月文件，时间序列查询也能按年拆开跑。对多因子研究来说，这两种查询都会出现，没必要为了其中一种把另一种做到极致。

文件内部按 `(trade_date, ts_code, trade_time)` 排序，同一交易日的股票连续存放。行组大约 100 万行，带 `trade_date` 的 min/max 统计，查某一天时只会读命中的行组。

## 怎么构建

源包每年一个 zip，里面是 `{年份}/1min/{code}.parquet` 和 `{年份}/day/stock_daily.parquet`。分钟数据每股一个文件，日线全年一个文件。

### 读 zip 里的 parquet

一开始我想让 pyarrow 直接在 zip 流里 seek，结果同一段数据会被解压两遍。后来改成把单个成员整块读进内存再解析：

```python
def read_min(f):
    t = pq.read_table(pa.BufferReader(f.read()))
    return norm(t, MIN_COLS)
```

单只股票的分钟文件不大，这个取舍比反复解压更划算。

### 按月份分桶

每读完一只股票，按 `trade_date` 拆成月份，放进对应的缓冲区。累计到约 300 万行就 flush 一次，写成 staging 目录下的临时 part。这样内存不会随年份增长，也不会每只股票都写一个小文件。

等一年读完，再把同一个月的 part 合并、排序、校验、写成最终文件。

### 统一 schema

前几年的源文件是旧版 pandas 写的，2026 年那批是新版，`ts_code` 的类型是 `large_string`，其余年份是 `string`。不统一的话，214 个分区会出现两种 schema，读起来很别扭。

脚本里显式 cast，列顺序也固定下来，不依赖源文件里 pandas 索引列的位置：

```python
if c == "ts_code":
    a = a.cast(pa.string())
elif c in ("trade_date", "trade_time"):
    a = a.cast(pa.timestamp("ns"))
```

### 排序、去重、原子写入

每个月的 part 合并后按主键排序。排序后如果相邻三列完全相同，就是主键重复；发现重复直接退出，不写半成品。

写文件先写 `.tmp`，再用 `os.replace` 替换目标文件。构建中断不会留下一个看起来正常、实际只写了一半的 parquet。

Parquet 参数是这几项：

```python
PQ_KW = dict(
    compression="zstd",
    compression_level=3,
    use_dictionary=True,
    write_statistics=True,
    version="2.6",
    row_group_size=1_000_000,
)
```

zstd 3 在压缩率和解压速度之间比较平衡；字典编码对日期和代码这种低基数列很有效；行组统计负责查询剪枝。

### manifest

每个输出文件的行数、字节数、md5、分片数，以及每个年份来自哪个 zip，都写进 `_manifest.json`。路径存的是相对路径，数据集整体挪到外接盘也不会失效。

md5 只能说明“文件没被改过”，不能证明内容对。内容对不对，要靠下面那步回源比对。

## 怎么校验

`02_verify.py` 做了七项检查：

| # | 检查                                          | 需要源包 |
| - | --------------------------------------------- | -------- |
| 1 | 分区文件数与 manifest 一致                    | 否       |
| 2 | 月份连续，2009-01 到 2026-10 无缺口           | 否       |
| 3 | 214 个文件 schema 完全一致                    | 否       |
| 4 | 逐分区、逐年行数与 manifest / 源 zip 记录一致 | 否       |
| 5 | `--md5` 时全量重算校验和                    | 否       |
| 6 | 每日档数分布（信息性输出）                    | 否       |
| 7 | 随机 30 个股票-日与源 zip 逐值比对            | 是       |

第 7 项是最关键的。比较的不是“差不多”，而是 `rtol=0, atol=0`，把 OHLC、成交量、成交额、复权因子逐列对齐：

```python
np.allclose(src[c], dst[c], rtol=0, atol=0, equal_nan=True)
```

源包删除前跑过一次，30/30 全部逐值相同。这一步才能说明重排没有改数值。只看行数的话，重复行、错位、类型转换都可能漏过去。

源包删掉之后，第 7 项跑不了，但 1–6 项还能独立运行。现在要体检数据，执行：

```bash
python -I _build/02_verify.py --out .
```

如果要连 md5 一起复核，加 `--md5`，会把 38 GiB 重新读一遍。

`04_audit.py` 负责统计，不读全量数据，只按文件分组算每年的股票数、交易日数、行数和档数分布，结果写到 `_build/_audit.json`。README 里的数字都从这里来，不是手填的。

## 数据里发现的几个问题

### 北交所不是 241 档

正常股票每天 241 档：09:30 集合竞价一档，09:31–11:30 一百二十档，13:01–15:00 一百二十档。北交所有些交易日是 271 档，多出 15:01–15:30 的盘后固定价格交易，全部是零成交量、价格冻在 15:00 的填充行。

全库 15,110,765 个股票-日里，241 档的有 14,918,919 个，271 档的有 191,846 个，后者全部是 `.BJ` 代码。按日 pivot 之前先过滤 `trade_time <= 15:00`，否则北交所股票会多出 30 行。

### 停牌在两张表里不一致

整日停牌时，日线表里没有这一天，分钟表里却有满 241 档的零成交量填充，OHLC 冻在停牌前收盘价。半天停牌两表都有行，日线用 `suspend_timing` 标出时段。

这意味着不能假设“有行就是有交易”。全库零成交量的股票-日有 379,324 个，占 2.5%，分布很不均匀：2014 年 8.1%，2019–2021 年只有 0.2%–0.4%。做日内因子或换手率之前，要么用 `sum(vol) > 0` 剔除，要么和日线 join，让日线的缺行自然过滤掉。

### 2009 年有 15 个坏文件

2009 年的源 zip 里有 15 个成员 CRC 校验失败或文件头不完整，读取时跳过了。影响的是这 15 只股票 2009 年的分钟数据，日线不受影响，前后年份也不受影响。构建时把文件名和错误写进了 manifest 的 `corrupt` 字段，日后重新拿到源包可以按年重跑补上。

### 2026 年不完整

数据只到 2026-10-23，2026 年 1–8 月是完整的，9–10 月可能还有遗漏。所以它是一份快照，不是完整年度。

### 单位和复权

分钟表 `vol` 是股、`amount` 是元；日线 `vol` 是手、`amount` 是千元。两表直接比会差 100 倍和 1000 倍。日线的股本是万股、市值是万元，换成股和元要乘 10,000。

价格全部是未复权原值，`adj_factor` 逐行保留：

```text
后复权价 = 原价 × adj_factor
前复权价 = 原价 × adj_factor / adj_factor_最新
真实收益率 = (close_t × adj_factor_t) / (close_{t-1} × adj_factor_{t-1}) − 1
```

日线的 `pre_close` 也不是前一日的 `close` 原值，而是按当日因子重算过的昨收，所以 `pct_chg` 已经是扣掉除权除息影响的真实收益率，可以直接用。

### 码表的四列是空的

`list_status`、`delist_date`、`is_hs`、`fill_source` 全空。码表里有 5,928 只证券，包含已退市的，但拿不到退市日期。要判断某只股票某天是否在市，只能看行情数据里有没有这一行。

另外北交所行情最早从 2022-07 开始。北交所 2021-11 开市，头 8 个月在这份数据里是缺的。

## 几个设计决定

**冻结，不做增量更新。** 这份数据是用来做本地因子研究的，不是生产行情服务。冻结之后每次回测的样本一致，结果可复现；代价是会过时。以后真要更新，得重新设计增量分区和版本管理，不能直接在现有文件上追加。

**存未复权价，不替使用者选复权基准。** 前复权还是后复权、基准日选哪天，都是分析决策。把基准冻进数据，等于替下游做了决定。存原价加因子，任何口径都能算出来。

**不聚合、不填充、不剔除。** 5/15/30/60 分钟线都可以从 1 分钟线聚合，保留等于同一份数据存六遍；停牌和北交所填充档保留原样，让使用者自己决定怎么处理。坏处是使用门槛高一些，好处是没有信息被提前丢掉。

**数据不进 Git。** 38.1 GiB 的 Parquet 不适合放仓库。仓库里只有 README、三个脚本、manifest 和 `.gitkeep` 占位目录。别人拿到仓库后，按 README 的结构把数据放回去，校验脚本就能直接跑。

## 现在回头看

这套东西现在还在用。最满意的是校验和构建分开：生成器可以写得很糙，但校验脚本必须能在源包删掉之后独立跑。manifest 用相对路径也是有意为之，数据整体挪位置不用改脚本。

回源逐值比对是花时间最多的一步，但也最值。只对行数的话，重复行、错位、类型转换都可能漏过去；30 个股票-日的逐值比对让我敢把源包删掉。

不满意的地方也很明确。数据只在我本地，没有对象存储备份，换机器要重新拷 38 GiB。2009 年那 15 只股票的分钟数据补不回来。校验脚本没接 CI，现在靠手动跑。没有质量看板，档数分布、零成交量比例这些指标要跑审计才看得到。

如果再做一遍，我会先把校验接进 CI，再考虑把数据放到对象存储。冻结数据适合复现，不适合实盘跟踪；以后真要做生产级数据服务，这套结构得重做。

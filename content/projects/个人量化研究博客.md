## 项目背景

这个站点最初只是为了有个地方放学习笔记。但写到后面，我发现自己需要的东西已经不是一个「通用博客模板」能装下的：

- **文章和研究笔记不是同一种内容。** 长文适合按时间排列；研究笔记需要回答「属于哪个方向、做到什么程度、一句话结论是什么」，还要能按方向聚合。
- **展示页不能靠编数字。** 如果站点要用于面试展示，首页的篇数、字数、书目数、方向进度就必须从真实页面算出来，而不是写死在模板里。
- **内容形态不止一种。** 除了 Markdown 长文，还有 PDF 书籍、研究状态、项目卡片和站点统计，它们需要不同的信息结构。
- **维护成本要足够低。** 没有数据库、没有后端，所有内容跟着 Git 走，推送即发布。

所以这个项目的目标不是「搭一个能看的博客」，而是把**写作、研究管理、资料归档和成果展示**放进同一套可持续迭代的静态站点里。

## 站点结构

截至 2026-10-31，站点的信息架构如下：

| 入口 | 作用 | 当前内容 |
|---|---|---|
| `/` | 统计首页 | 90 篇文章、约 48 万字（含研究笔记与复盘，站点统计口径）、6 本书 |
| `/blog/` | 按时间排列的技术长文 | 72 篇，覆盖教程、量化、机器学习 |
| `/factor/` | 多因子研究仪表盘 | 6 个研究方向、4 篇研究笔记 |
| `/cta/` | CTA 研究仪表盘 | 6 个研究方向、1 篇研究笔记 |
| `/reviews/` | 每日交易复盘 | 13 篇，按交易日记录盘面判断、截图证据与事后反思 |
| `/books/` | 书籍与 PDF 阅读 | 6 本书，含封面、书目信息和在线阅读 |
| `/projects/` | 项目展示 | 当前项目 |
| `/search/` | 站内搜索 | 索引文章、研究笔记、复盘与书籍 |
| `/about/` | 个人介绍 | 学习方向与联系方式 |

这里有一个刻意做出的边界：`mainSections` 只包含 `post`。因此多因子、CTA 的研究笔记和每日复盘可以被搜索到、可以在各自页面里聚合，但**不会**混进 `/blog/`、归档页和主 RSS。展示时是研究体系，阅读时仍然是干净的文章流。

## 内容体系

技术栈只是这个项目的一半，另一半是站点里实际沉淀的内容。

**技术长文**按主题分成六个系列：

- Freqtrade 课程：36 篇，从环境搭建到策略编写与实盘部署
- Freqtrade 策略库：21 篇，包含可运行策略与「前视偏差」反面教材
- 华泰多因子研报复现：4 篇，从因子体系到回测与 Streamlit 展示
- 技术栈：8 篇，覆盖 BackTrader、DuckDB + Parquet、MySQL、CCXT、Streamlit、云服务器部署等
- 数学教程与机器学习：数学教程 2 篇、机器学习 1 篇，记录基础概念的系统梳理

**研究笔记**不追求「篇数」，而是按方向维护状态。以多因子为例，`data`、`construction`、`engineering` 等方向各自有定义、研究问题和当前结论；每篇笔记都带 `group`、`status` 和 `summary`，仪表盘据此自动统计进度。已经落地的四篇分别讨论因子构建方法、单因子回测框架、行情数据整理和因子预处理；CTA 侧则先把宏观研究方向的系统性框架整理成一篇长笔记。

**每日交易复盘**是第三种内容形态：按交易日组织，一篇一个页面包，正文是当天的判断与反思，截图作为页面资源直接引用。它记录的是真实的交易过程和情绪，不做修饰，也不构成投资建议。列表页按月分组，卡片带时段和截图缩略图。

**书籍书架**收录了 6 本与量化、机器学习相关的书，每本书是一个页面包：书目信息、封面和 PDF 放在一起，点开即可在站内阅读。

写作上有一条硬规则：**页面上出现的数字必须来自真实页面或真实计算**。统计页的篇数、字数、书目数、分类分布、贡献热力图全部由 Hugo 在构建时从内容里算出来；研究仪表盘的方向进度也来自笔记的 front matter。没有「示例数据」，也没有为了好看而填的指标。

## 技术栈

- **站点生成**：Hugo Extended，本地版本 0.161.1；CI 使用 `latest` extended 版本
- **主题**：Hugo Theme Stack v4.0.0-beta.15，以 Hugo Module 方式引入，而不是复制主题源码
- **语言与构建**：Go 1.25、Dart Sass 1.97.1
- **样式与交互**：SCSS 自定义组件、原生 JavaScript（统计图表与热力图）、CSS 变量与暗色模式
- **内容格式**：Markdown、YAML front matter、KaTeX 数学公式、Page Bundle 资源管理
- **部署**：GitHub Actions 构建，`upload-pages-artifact` + GitHub Pages 发布
- **搜索**：构建时生成 JSON 索引，前端检索文章、研究笔记、复盘和书籍

内容与构建链路没有数据库、没有服务端进程，评论由外部 Waline 服务承担。内容、模板、样式全部在同一个 Git 仓库里，构建产物是纯静态文件。

## 我做了什么

### 1. 研究仪表盘

`layouts/_partials/research/dashboard.html` 和 `note-row.html` 是我为多因子、CTA 两个分区写的核心组件，配合 `layouts/factor/list.html`、`layouts/cta/list.html` 使用。

它不是把文章列表换个样式，而是把「研究方向」当成一等对象：

- 方向定义写在 `_index.zh.md` 的 `directions` 里，包含 id、名称、研究问题、简介和状态
- 每篇笔记通过 `group` 归属方向，通过 `status` 标记探索中 / 进行中 / 已完成 / 暂停
- KPI、方向笔记数、完成数、最近更新时间全部从 `.RegularPages` 实时计算
- `group` 写错时页面会显示「未归类」并触发构建警告，避免笔记悄悄消失
- 零笔记、缺 summary、缺状态都有空状态回退，不会出现空白卡片或假数据

这样我新增一篇笔记时，只需要写 front matter，仪表盘会自动更新；不需要手动改任何统计数字。

### 2. 统计首页

`layouts/_partials/stats/dashboard.html` 同时服务首页和 `/stats/`，包含：

- 文章数、总字数、运行天数、已有复盘篇数、已有书目五张摘要卡
- 分类与标签分布
- 年度文章贡献热力图
- 按星期和小时统计的写作习惯图

文章数和字数来自 `post`、`factor`、`cta`、`reviews` 四个分区的 `.RegularPages` 与 `.WordCount`，书目数来自 `books` 分区，热力图数据来自每个内容页的发布日期。运行天数由前端根据站点起始时间计算。所有统计口径都写在模板里，不依赖外部分析服务。

### 3. 书籍书架

`layouts/_partials/books/card.html`、`layouts/books/list.html`、`layouts/books/single.html` 组成完整的书籍浏览与阅读体验：

- 每本书使用 Page Bundle：`index.md` + `book.pdf` + `cover.jpg`
- 列表页读取封面生成卡片；单页用 iframe 嵌入 PDF，并提供下载入口
- 缺少 PDF 或封面时给出明确的构建警告和视觉占位，而不是渲染破图
- 书目信息（作者、出版社、年份、标签、简介）都在 front matter 中维护

### 4. 搜索索引覆盖

我覆盖了主题的 `layouts/page/search.json`，把索引范围从 `post` 扩展到 `post`、`factor`、`cta`、`books`、`reviews`，并把 `summary` 和作者信息拼进检索内容。因为 `mainSections` 没有改，研究笔记和复盘进入搜索的同时，文章流、归档和 RSS 仍然只包含长文。

### 5. 样式与交互

`assets/scss/partials/custom-components/` 下按功能拆分了书籍、代码块、页脚、首页网格、移动端菜单、研究仪表盘、时间线、标题和排版等样式；图标使用自定义 SVG，跟随主题色变化。统计页和研究页的响应式布局、暗色模式适配也都在这一层完成。

### 6. 内容工作流

- 用 archetype 和 Page Bundle 统一新文章、研究笔记、书籍的目录结构
- 数学公式通过 KaTeX 渲染，长文中的公式和代码块保持可复制
- 构建命令固定为 `hugo --gc --minify`，部署由 GitHub Actions 完成
- 发布前检查内部锚点、搜索命中和页面返回状态，避免目录链接失效

## 关键取舍

**静态优先。** 没有自建后端意味着不能做登录、复杂的实时交互和自定义服务端逻辑，但换来的是极低的维护成本、免费的托管、天然的版本历史和很快的访问速度。评论交给外部 Waline 服务，站点本身仍然保持静态。

**内容分区而不是堆在一个列表里。** 研究笔记和长文共享同一套 Hugo 内容系统，却有不同的聚合方式。代价是多写了一些模板和 front matter 约定，收益是面试官能按研究方向看到完整脉络，而不是在几十篇文章里翻找。

**数字只来自内容。** 统计页不接第三方统计服务，也不手写「累计 xx 万字」。好处是永远不会出现展示页和实际内容对不上的情况；代价是每次构建都要遍历页面，内容变多后构建时间会上升。

**图片和 PDF 跟着页面走。** 正文图片放在 Page Bundle 里，避免外链失效或路径错误导致静默破图。书籍 PDF 让仓库体积明显增大，这是这个项目最直接的工程代价。

## 当前状态与复盘

截至 2026-10-31 的规模是：90 篇内容（72 篇长文 + 5 篇研究笔记 + 13 篇交易复盘）、约 48 万字、6 本书、两个各含 6 个方向的研究分区。本地 `hugo --gc --minify` 构建通过，GitHub Actions 推送到 `main` 后自动发布到 GitHub Pages。

做得比较好的地方：

- 把「研究进度」变成了可计算的数据结构，而不是一段手写的自我介绍
- 展示页的每个数字都能追溯到真实页面
- 书籍、研究笔记、长文共用一套静态内容系统，没有引入额外服务
- 自定义模板都考虑了空状态和资源缺失，内容不完整时不会渲染出坏页面

仍然不够好的地方：

- 研究笔记数量还少，多因子和 CTA 的多数方向只有定义，没有形成连续的验证记录
- 书籍 PDF 让仓库和发布产物体积偏大，后续需要考虑更轻的存储方式
- 站内搜索是构建时全量索引，内容继续增长后需要关注索引体积和加载时间
- 目前没有把链接检查、锚点检查放进 CI，发布前仍依赖手动验证
- 评论仍在使用主题配置里的 Waline 演示服务地址，尚未接入自己的服务端
- 统计页只覆盖内容本身，没有阅读量、访问来源等流量数据

下一步我更想补的是内容而不是功能：把多因子的因子构建、检验和回测记录连成线，把 CTA 的趋势与组合方向逐步填满，同时把剩余的远程图片迁进 Page Bundle，并把发布前的检查脚本固化到 CI 里。

## 这个项目说明了什么

它不是一个「用了哪些框架」的清单，而是一次完整的内容产品实践：先明确读者是谁、内容如何组织，再决定数据模型和模板；先保证数字真实、链接可用、缺资源时有回退，再考虑视觉效果。

对我来说，这个站点最重要的产出不是页面本身，而是它把学习记录、研究进度和成果展示变成了一个**可以持续维护的系统**——每写一篇笔记，首页和研究仪表盘都会自动反映真实进展。
